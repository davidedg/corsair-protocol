# Corsair K95 RGB Platinum (`1b1c:1b2d`): on-board profiles

The K95 RGB Platinum keeps **three profiles in its flash memory** and runs the active one by itself when no software drives it (hardware mode): key remaps, macros, texts, key combinations, lighting layers and effects, indicator colours and Win Lock options. The profiles are files of a small file system, reached through field `0x17` of the protocol. This page is the map of what is known about it; the commands and the file formats have pages of their own.

**Scope.** Everything here was seen on a K95 RGB Platinum with **firmware 3.29 and bootloader 3.03** (`0e 01` bytes 8 to 11: `29 03 03 03`), unless it is marked *(inferred)*. Another firmware level exists (3.08, bootloader 0.04, [`0e 01`](../host-to-device/0e/01/0e01.md)); nothing here was checked on it. iCUE 5, Corsair's own software, is the reference implementation: where these pages say what iCUE writes, they describe its behaviour with this keyboard.

**Implementation.** [davidedg/ckb-next-ddg](https://github.com/davidedg/ckb-next-ddg), a fork of ckb-next, reads and writes these profiles. It is experimental: its daemon needs `--enable-experimental`, and its README has a warning to read first.

## What the keyboard does on its own

| Feature | Stored in |
|---|---|
| Remap a key to another key (media keys and the profile, brightness and Win Lock buttons included, as source and as destination) | [PROFILE.MAP](../formats/cape/profile-map.md) |
| Remap a key to mouse button 1 to 5 | [PROFILE.MAP](../formats/cape/profile-map.md) |
| Recorded macro: key presses, releases and delays, constant or random | [PROFILE.DAT](../formats/cape/profile-dat.md) and a [macro file](../formats/cape/macro.md) |
| Text typed by the keyboard, with a delay between characters | the same (a macro) |
| Key combination, and a remap that holds the key for a time or repeats it ("Imitate holding key") | the same (a macro) |
| An action on press, on release, while pressed, or as a toggle | [PROFILE.DAT](../formats/cape/profile-dat.md) |
| Static lighting: up to 5 layers of one colour each, with an opacity, painted over one another | [lighting](../formats/cape/lighting.md) |
| Custom lighting effects (Solid, Gradient, Ripple, Wave), mixed with static layers, up to 5 layers | [custom effects](../formats/cape/custom-effects.md) |
| One predefined lighting effect, alone (8 kinds) | [predefined effects](../formats/cape/predefined-effects.md) |
| Colours of the profile, brightness and Win Lock buttons | [PROFILE.I](../formats/cape/profile-i.md) |
| What Win Lock disables (Windows key, Alt+Tab, Alt+F4, Shift+Tab) | [PROFILE.DAT](../formats/cape/profile-dat.md) |
| Name, GUID and revision of the profile | [PROFILE.I](../formats/cape/profile-i.md), slot table |

Not on the keyboard: a "disable key" action, a "switch profile" action, launching programs, mouse movement; iCUE runs those itself while it holds the keyboard. The host cannot change the active slot, nor read which one it is: only the profile button changes it.

## Transport

- Packets are 64 bytes, padded with zeros. With a plain HID stack the commands are written to interface 1 (vendor usage page `FFC2`, usage 4; output report of 65 bytes with report ID 0), and the replies arrive on interface 0, in the collection of usage page `FFC2`, usage 3 (input report of 64 bytes, whose first byte is the report ID: `0e`, ...).
- `07` and `7f` packets get no reply; `0e` and `ff` packets get one.
- **A reply echoes the first 2 to 4 bytes of the command, and the keyboard reuses one reply buffer**: the bytes a command does not write still hold the previous reply. Read only the bytes documented for each command. An unknown `0e 17 xx` is answered with the stale buffer (byte 4 = `55`), not with an error.
- File data travels in **chunks of at most 60 bytes**, in **bursts of at most 5 chunks** (300 bytes, the transfer buffer of [`0e 17 01`](../host-to-device/0e/17/01/0e1701.md)): [`7f NN SS 00`](../host-to-device/7f/NN/SS/00/7fNNSS00.md) to write, [`ff NN LL 00`](../host-to-device/ff/NN/LL/00/ffNNLL00.md) to read.

## Sequences

### Enumerate the slots

```
> 0e 17 04 00
< 0e 17 04 00 | 1a a3 48 4e ce ce 4c 3e 87 b4 75 df 2f cd b6 3a | dd 02 00 | 01 |   slot 0: GUID, cookie 733
                f7 0c d7 9d 00 fe 4e cb 8d 6f 5d bc b2 cc e5 2a | 77 06 00 | 01 |   slot 1: GUID, cookie 1655
                00 ×20                                                             slot 2: empty
```

### Read a file

```
> 07 17 0c 00                                   select slot 0
> 07 17 07 00 50 52 4f 46 49 4c 45 2e 49 00     open "PROFILE.I" for reading
> 0e 17 0d 00          < 0e 17 0d 00 00 ...     status 0 (a missing file gives 04: close and skip)
> 0e 17 03 01          < 0e 17 03 01 0c 01 00 00 ...   size 268
loop while bytes remain (300 per burst):
  > 07 17 0a                                    fill the read buffer from the file
  > 0e 17 0d           < ... 00                 status 0
  > ff 01 3c 00        < 0e ff 01 3c 49 00 1a a3 48 4e ... (60 bytes of data from byte 4)
  > ff 02 3c 00        < 0e ff 02 3c ...
  ...                                           up to ff 05, last chunk may be shorter (e.g. ff 05 1c = 28 bytes)
> 07 17 08                                      close
```

A file costs 4 packets, plus 2 and one per 60 bytes for each burst of 300: `PROFILE.I` is 11 packets (12 with the slot selection), a missing file 3.

### Write a slot

A slot is always rewritten whole: the files the new profile has, in this order, between clearing the slot entry and setting it again.

```
> 07 17 0c SS                                   select slot SS
> 0e 17 03 00                                   (informative) slot size
> 0e 17 0b 00                                   free space
> 07 15 SS 00 <20 zeros>                        clear the slot GUID
> 0e 17 0d 00          < status 0               (can take up to 2.2 s to answer)
> 07 17 0e                                      transaction marker → slot is now empty
> 07 15 SS 00 <GUID> <cookie u24 LE> 01         set GUID + cookie
> 0e 17 0d 00          < status 0
> 07 17 0c SS                                   select slot again
for each file, in this order: M000, M001, …, PROFILE.DAT, PROFILE.I, PROFILE.MAP, PROFILE.ZIP, lght_00.d [, lght_00.k, lght_00.r, lght_01.*…], lghtcnt.cnt
  > 07 17 05 00 <name>                          open for writing
  > 0e 17 0d 00        < status 0
  for each burst of ≤300 bytes:
    > 7f 01 LL 00 <data>  …  > 7f 05 LL 00 <data>
    > 07 17 09                                  commit burst
    > 0e 17 0d 00      < status 0
  > 07 17 08                                    close
> 07 17 0e                                      transaction marker (end)
> 0e 17 0d 00          < status 0
```

- The macro files come before `PROFILE.DAT`, which names them; the layers bottom first, each `.d`, `.k`, `.r`; `lghtcnt.cnt` last. `PROFILE.ZIP` is iCUE's own copy of the profile: the firmware does not need it. A slot written without it works on the keyboard, but iCUE 5 shows that slot as empty: it does not rebuild a profile from the other files.
- **Timing of iCUE.** The chunks of a burst and their `07 17 09` go about 1 ms apart; every other packet 10 to 22 ms after the one before (about 11 ms), once the reply to a query has arrived. The keyboard takes, from a status query to its reply: 0.2 to 2.2 s after the clear (more for a slot with more files), about 0.4 s after setting the entry, 0.1 s after an open, 40 ms after a burst, 0.3 s after the closing `07 17 0e`. iCUE writes a slot of five static layers in 7.5 to 8.5 s, and reads nothing of the slot before or after.
- A write of the active slot does not change its remaps and macros until the slot is switched away and back with the profile button. Its lighting, indicator colours and Win Lock options show as soon as the keyboard is back in hardware mode.

### Delete a slot

```
> 07 15 SS 00 <20 zeros>
> 0e 17 0d 00          < status 0
> 07 17 0e
```

The slot table then shows 20 zero bytes for the slot and its size is 0. There is no command to delete a single file, and none is needed.

### Back to hardware mode

To give the keyboard back to hardware mode, send [`07 04 01`](../host-to-device/07/04/070401.md) once, as iCUE does when it closes. **Do not write a key input table that sets the G keys and the profile button to HID only** ([`07 40 NN 00`](../host-to-device/07/40/NN/00/0740NN00.md)) with its `07 05 02 00 03 00`: that leaves the keyboard without its hardware macros and its profile button until it is power cycled.

## Slots

- **Numbering.** The firmware numbers the slots 0 to 2; iCUE shows them as 1 to 3 ("HW Profile 1" is slot 0).
- **Files.** A slot holds the files of [the file formats](../formats/cape/README.md): `PROFILE.I`, `PROFILE.MAP`, `PROFILE.DAT`, the macro files, `lghtcnt.cnt` and the files of the layers, and iCUE's `PROFILE.ZIP`. A slot is a profile on its own, identified by its GUID and its revision cookie: there is no profile object above the three slots.
- **The active slot.** Only the profile button changes it (1, 2, 3, 1, ...). No host command changes or reads it: [`07 17 0c`](../host-to-device/07/17/0c/0X/07170c0X.md), `07 04 01`, `07 04 02` and `07 17 0e` were tried, and the unknown reads of field `0x17` return the stale buffer. In software mode a press of the profile button reaches the host as the Corsair event of the button, and does not switch slot. When iCUE closes, the keyboard resumes the slot it had before iCUE started.

## Behaviour

- **iCUE at start** reads the slot table and the `PROFILE.I` of each slot in use, then shows the profiles from its own local copy as long as GUID and cookie match. For a slot it has no copy of (or, *inferred*, a copy that does not match) it also reads the slot's `PROFILE.ZIP`, and the other files of a slot that has none. It does not write to the slots at start; it writes a slot only when a profile is saved in it. Switching profile in iCUE's interface sends no command to the slots: in software mode iCUE runs the profiles itself.
- Reading the files does not change the active slot. **A read made in hardware mode leaves the keys dark** (seen with an active slot of static layers; whether an effect stops as well is not known): the lighting of the active slot comes back with one [`07 04 01`](../host-to-device/07/04/070401.md), also when the keyboard is already in hardware mode. iCUE reads only in software mode, and sends `07 04 01` when it closes.
- In software mode the firmware does not run the macros of the active profile ([`07 04 02`](../host-to-device/07/04/070402.md)); after the hand-back with `07 04 01`, remaps, macros and lighting effects run again.
- A key remapped to a mouse button sends the mouse report [`05`](../device-to-host/05/05.md) in hardware mode.

## Implementation notes

What a host that reads and writes the on-board profiles has to respect, beyond the sequences above.

**Session**

- Identify the keyboard first (`0e 01`) and touch the file system only at a firmware level known to work: 3.29 / 3.03 is the only one checked.
- Then [`0e 17 01`](../host-to-device/0e/17/01/0e1701.md) (300 expected) and [`0e 17 04`](../host-to-device/0e/17/04/0e1704.md) (each entry all zeros or ending in `01`). One [`07 17 08`](../host-to-device/07/17/08/071708.md) closes a file that an interrupted session may have left open.
- Status ([`0e 17 0d`](../host-to-device/0e/17/0d/0e170d.md)): `00` done; `04` after an open, a missing file (close it and go on); `04` anywhere else and `0d`, an error; any other value, ask again (for example up to 50 times, 20 ms apart), then give up.
- The protocol has no request identifier: a stale reply of the same command cannot be told apart from a new one. Check that every reply starts with the bytes of its command (`0e ff NN LL` for a chunk), and end the session cleanly on a reply that does not.

**Reading**

- [`07 17 0a`](../host-to-device/07/17/0a/07170a.md) before **every** burst of reads; the size of a file from [`0e 17 03 01`](../host-to-device/0e/17/03/01/0e170301.md) after its open, not from `0e 17 03 00` (the whole slot) and not assumed.
- Skip the slots whose entry is all zeros.
- Read a layer's `.d` first: its size and byte 0 say which of `.k` and `.r` exist ([lighting](../formats/cape/lighting.md)). A predefined effect has neither.
- Accept only what has been seen: `lghtcnt.cnt` 0 to 5, a `.d` whose size matches its type, a `.k` whose count matches its length, layers all of the custom kind or one predefined effect. Keep anything else byte for byte, as unknown.
- To show the static picture of a slot, composite its layers over one another in file order ([lighting](../formats/cape/lighting.md#how-the-firmware-paints-the-layers)); the three buttons take the indicator colours of [PROFILE.I](../formats/cape/profile-i.md) (the Win Lock button its off colour at rest).
- A slot with many long texts can take thousands of packets to read; iCUE itself reads only `PROFILE.I` at start when its local copy matches.
- After a read made in hardware mode, send one `07 04 01`: the read left the keys dark ([behaviour](#behaviour)). In software mode the host paints the keys anyway.

**Writing**

- Read the slot first, change what is to change, write only that slot, then read it back and compare.
- **Never repeat a packet of a write (`07` or `7f`) after it failed**: the flash may have taken it. A repeated query (`0e`, `ff`) is harmless. Do not reset the device and repeat a command on a status error.
- Pace as iCUE does: the chunks of a burst back to back (about 1 ms), about 11 ms between the other packets, and wait for each status reply (up to a few seconds after a clear). Reads worked with 1 ms between packets.
- Check the free space before clearing the slot: the new files must fit in the free sectors, the slot's old files counting as used ([space](../formats/cape/README.md#space)).
- `07 15 SS 00` takes the slot index in byte 2 and the whole 20-byte entry: GUID, cookie (u24), `01`. Each slot has its own GUID and cookie, the same in its `PROFILE.I` (where the cookie field is 4 bytes). Raise the cookie at every save; it has 24 bits (iCUE wraps it after `0xfffffe`).
- Patch the `PROFILE.I` that was read rather than build a new one: a longer name and the bytes not understood must survive.
- Keep what is not understood, and the lighting effects, byte for byte.
- Static colours: one layer per colour, at most five; a black layer is not needed (a key in no layer is dark). Build `.k` from the real cells of the keys, in iCUE's order ([lighting cells](../formats/cape/lighting-cells.md)), never outside the 135 cells; `.r` is a compact list, entry *i* for the *i*-th cell of `.k`.
- Write macro events as iCUE writes them ([macro files](../formats/cape/macro.md)): short delays below 8192 ms, long delays from there.
- After the write, if the remaps or macros of the active slot changed, a switch of slot with the profile button (away and back) is needed for them to take effect: say so.

**Leaving**

- Hand the keyboard back with one `07 04 01`, no key input table ([back to hardware mode](#back-to-hardware-mode)).
- While the host holds the keyboard in software mode it gets the profile button as a Corsair event; in hardware mode it must take the mouse report `05` as mouse input.

## Open questions

- How the custom effects and a predefined effect combine with static layers on the keyboard; the firmware's exact blending arithmetic.
- Values never seen: EffectType 14, colour type 2, duration short, direction 7.
- How a mouse button would appear inside a macro file; whether byte 2 of a macro header belongs to the event count; what exactly the firmware does with run type `04`; what bit 7 of run type `84` means alone; what it does with a short delay whose first byte is `a0` to `bf`.
- How exact the firmware's delays are: measurements gave between 90 % and 99 % of the time written.
- Whether a USB reset makes the firmware reload the remaps and macros of the active slot; which packet of a read stops the hardware lighting, and whether an effect stops too.
- The parameter of `07 17 0e`; the reply of `0e 05`, which differs between the two firmware levels.
- Whether the firmware applies the remaps of `PROFILE.MAP` in software mode.
- How many files the file system can hold.
- Other firmware levels and other operating systems than the ones these facts come from.
